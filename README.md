# Smart Expense Tracker API

A small REST API for recording and reviewing personal expenses. It supports creating expenses, listing them, filtering by category, calculating totals, and deleting entries.

The application is written in Node.js using Node's built-in HTTP server. It intentionally uses in-memory storage, so there is no database setup and all data is cleared when the server stops. This is appropriate for the scope of the assignment.

## Requirements

- Node.js **20 or newer** (Node 24 was used to verify this project)
- npm (installed with Node.js)

## Install dependencies

Run this from the repository root:

```bash
npm install
```

There are currently no third-party runtime packages, but this command is included so the setup process is stable and follows standard Node.js project conventions.

## Start the server

```bash
npm start
```

The server starts at `http://localhost:3000`.

To run it on a different port:

```bash
PORT=4000 npm start
```

On Windows PowerShell, use:

```powershell
$env:PORT=4000; npm start
```

## Run the tests

```bash
npm test
```

The test suite starts an isolated server for each test, sends real HTTP requests, and checks the main success and error cases. The exact install and test commands above were run successfully before submission.

## API overview

Every expense has the following shape:

```json
{
  "id": "generated UUID",
  "title": "Groceries",
  "amount": 54.25,
  "category": "Food",
  "date": "2026-08-01"
}
```

`id` is generated by the server when an expense is created. `amount` must be a positive value with no more than two decimal places. `title` and `category` must be non-empty strings (up to 200 and 100 characters respectively). `date` must be a real calendar date in `YYYY-MM-DD` format. Unknown JSON properties are rejected, which helps catch misspelled field names.

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/expenses` | Create an expense |
| `GET` | `/expenses` | Return all expenses |
| `GET` | `/expenses?category=Food` | Return expenses in one category |
| `GET` | `/expenses/total` | Return the overall total and count |
| `GET` | `/expenses/total?category=Food` | Return the total and count for one category |
| `DELETE` | `/expenses/:id` | Delete an expense by ID |
| `GET` | `/health` | Simple health check |
| `GET` | `/api-docs/openapi.json` | OpenAPI 3.0 API description (bonus feature) |

## Example requests

### Create an expense

```bash
curl -X POST http://localhost:3000/expenses \
  -H "Content-Type: application/json" \
  -d '{"title":"Groceries","amount":54.25,"category":"Food","date":"2026-08-01"}'
```

Example response (`201 Created`):

```json
{
  "data": {
    "id": "e5821b90-1bb7-4e03-a6d8-7f802578726d",
    "title": "Groceries",
    "amount": 54.25,
    "category": "Food",
    "date": "2026-08-01"
  }
}
```

### List all expenses

```bash
curl http://localhost:3000/expenses
```

### Filter by category

```bash
curl "http://localhost:3000/expenses?category=Food"
```

Category matching is exact and case-sensitive (for example, `Food` and `food` are separate categories).

### Get totals

```bash
curl http://localhost:3000/expenses/total
curl "http://localhost:3000/expenses/total?category=Food"
```

Example category-total response:

```json
{
  "data": {
    "category": "Food",
    "total": 54.25,
    "count": 1
  }
}
```

### Delete an expense

Replace `<id>` with the ID returned when the expense was created:

```bash
curl -X DELETE http://localhost:3000/expenses/<id>
```

The endpoint returns `204 No Content` when deletion succeeds and `404 Not Found` if that ID does not exist.

## Error responses

Validation errors return `400 Bad Request` in a consistent format. The API rejects invalid or impossible dates, non-positive or fractional-cent amounts, blank/oversized text, repeated or blank `category` filters, and unexpected JSON fields. `POST /expenses` requires an `application/json` content type; request bodies are limited to 1 MB. For example:

```json
{
  "error": {
    "message": "Validation failed",
    "details": [
      "amount must be a positive number"
    ]
  }
}
```

Unknown routes and missing expense IDs return `404`. Malformed JSON is also reported as `400`.

## Validation and edge cases

The API deliberately validates more than just the happy path:

| Area | Rules enforced |
| --- | --- |
| Request body | Must be a JSON object using `Content-Type: application/json`; maximum size is 1 MB |
| Accepted fields | Only `title`, `amount`, `category`, and `date` are accepted; unexpected fields are rejected |
| Title | Required after trimming whitespace; maximum 200 characters |
| Category | Required after trimming whitespace; maximum 100 characters |
| Amount | Must be a finite, positive number with at most two decimal places |
| Date | Must use `YYYY-MM-DD` and be a real calendar date; for example, `2026-02-30` is rejected |
| Category filter | May appear at most once, cannot be blank, and has the same 100-character limit |
| Totals | Summed in cents, avoiding floating-point inaccuracies such as `0.1 + 0.2` becoming `0.30000000000000004` |
| Deletion | Returns `404 Not Found` when the requested expense ID does not exist |

## Test coverage

`npm test` runs five integration tests against temporary HTTP servers. They cover all five required assignment features—create, list, filter, overall/category totals, and delete—plus validation failures, malformed request shapes, unsupported content types, unknown fields, repeated filters, missing IDs, accurate money totals, and the OpenAPI endpoint.

## Project structure

```text
src/
  app.js                    HTTP request routing and response handling
  controllers/              HTTP-facing request handlers
  services/                 Business rules and total calculations
  repositories/             In-memory expense storage abstraction
  validators/               Request validation
  errors/                   Application error type
  openapi.js                OpenAPI documentation
  server.js                 Application entry point
tests/
  expenses.test.js          End-to-end API tests
```

## Design notes

The code keeps transport concerns, business rules, and storage separate. This makes it straightforward to replace the in-memory repository with a file or database-backed implementation later without changing the API contract or total-calculation logic. The single optional bonus selected for this submission is OpenAPI documentation, available at `/api-docs/openapi.json`.
